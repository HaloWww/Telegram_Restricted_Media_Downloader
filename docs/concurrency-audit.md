# 下载并发问题分析与修复

## 执行路径

机器人消息由 Kurigram dispatcher 的有限数量 worker 处理。原来的普通链接入口已经创建后台任务，但发送/转发媒体、下载后上传、频道扫描、上传和回调入口仍会等待耗时工作。增加下载并发数无法解决 dispatcher worker 被占满的问题；同步文件操作还会阻塞所有 worker 共享的 asyncio 事件循环。

现在耗时入口只向统一的后台任务集合提交工作，立即归还 dispatcher worker。下载请求解析出媒体后，每个文件分别登记准备任务，在自己的协程内完成命名、等待文件锁、获取下载空位和传输。状态查询、命名按钮和取消操作可以独立执行。bot-client 的传输并发数也使用下载配置。

## 检查结果

| 原问题 | 影响 | 修复 |
| --- | --- | --- |
| 部分 handler 直接等待空位、命名、上传或扫描 | 多任务耗尽消息处理 worker，查询和按钮排队 | 耗时 handler 交给有生命周期管理的后台任务 |
| 等待任务取消仅设置标记 | 协程仍等待 semaphore 或命名超时 | 保存协程句柄并直接 cancel，清理任务登记 |
| 媒体组只有第一个文件登记为等待任务，共享可变 retry 参数 | 其他成员不可查看/取消，命名和重试状态相互覆盖 | 每个文件独立登记，复制 retry 和上传参数 |
| 下载空位、内存和进度依赖完成回调的正常路径释放 | 准备失败或取消后可能漏释放，队列永久等待 | 准备与完成阶段统一清理；协程尚未启动就被取消也有清理回调 |
| 主循环使用 queue.empty 判断是否还有下载 | 异步准备和重试还没入队时可能提前结束 | 跟踪准备、传输、重试、完成通知等后台工作；退出时停止客户端与上传 worker |
| 写文件、跨盘移动、终端命名输入、上传散列和媒体信息读取同步执行 | 慢磁盘、大文件或输入等待阻塞事件循环 | 在线程执行这些耗时工作；取消写入时等待当前写操作结束再关闭文件 |
| 同一保存路径可同时被多个任务写入 | 缓存损坏、文件移动冲突 | 文件路径锁覆盖准备、传输和落盘过程，释放后重新检查已下载文件 |
| FloodWait 后使用旧 offset；已有缓存末尾不足一整块 | 重复追加数据、断点文件损坏 | 每次重开流使用当前偏移，未完整的块尾重新下载；明确关闭流以释放传输 semaphore |
| 移动失败仍返回成功，磁盘下载异常没有读取 result | 错误的成功统计和后续上传 | 观察传输异常，验证文件移动结果，失败进入重试 |
| 重试重新初始化整个链接的完成记录 | 媒体组已成功成员丢失，完成通知不准确 | 重试保留完成记录；只有所有成员完成才登记链接成功 |
| 缓存 Telegram session 早于 start/import 完成 | 并发任务取到半初始化会话 | 同一 DC/session 类型串行初始化，成功后缓存，失败或取消后停止会话 |
| RPC 取消不清理 pending results | 残留响应记录不断增长 | send 的 finally 始终清理 pending result |
| 所有任务和取消按钮放在一条消息里 | 超过 Telegram 长度限制，后面的任务无法操作 | 每页 6 个任务，翻页与刷新携带页码，按原权限过滤 |
| 通知永久失败后直接再次循环 | 连续错误导致事件循环忙循环 | 非 FloodWait 错误记录后结束；限流仍按要求等待 |

## 验证

使用 Python 3.13 与 requirements.txt 中的依赖运行：

```sh
python -m compileall -q module tests
python -X utf8 -m unittest discover -s tests -v
```

24 项离线回归覆盖：空位占满时查询及取消、dispatcher 及时返回、媒体组独立排队、命名等待取消、准备失败释放内存与空位、启动前取消、完成处理启动前取消、跨用户权限隔离、100 个任务分页、部分块续传、限流续传、慢磁盘响应及关闭流、重复文件串行处理、实际失败重试与 CLI 等待重试、内存落盘、会话初始化竞争及取消、RPC 取消清理、终端命名等待、上传散列和永久通知错误。测试会检查意外的后台异常。

GitHub Actions 在 Windows 和 Linux 上运行这些检查。测试不登录 Telegram，不读取真实会话，不下载真实媒体。真实 Telegram 网络、服务端限流及长时间生产负载仍需在实际运行环境观察。

取消后的磁盘缓存保留用于续传。正在执行的单次磁盘写入或移动必须结束后才能完成资源清理；线程无法强制中断该系统调用，但事件循环会继续处理查询和其他任务。保存文件的命名规则保持既有规则，路径锁不会改变不同频道存在同名文件时的文件身份判定。
